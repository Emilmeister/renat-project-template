# Исполняемые спецификации поведения

Порядок работы и границы разрешений определены в
[workflow.md](workflow.md), окружение и реальные команды — в
[development.md](development.md).

## Область применения и движок

Спецификации наблюдаемого поведения продукта состоят из сценариев Gherkin
в `.feature` и исполняющих их проверок. Для Python используй pytest-bdd;
для другого стека — совместимый с ним BDD-движок, исполняющий Gherkin.

<remove_after_instruction_complete>

При первом подключении BDD зафиксируй выбранный движок и проверенную настройку
в `development.md`. После этого удали этот блок.

</remove_after_instruction_complete>

Обычные тесты с названиями `describe`/`it` сами по себе не заменяют этот формат.
При несовместимости с ограничениями проекта обозначь конфликт, не выбирая
молча другой формат или второй язык реализации.

Просьбы «напиши спецификации», «добавь спеки» или «подготовь критерии приёмки»
для поведения продукта означают этот исполняемый формат, если пользователь
явно не ограничил задачу обсуждением или другим результатом.

При новом или изменённом продуктовом поведении проверь, какие обязательства
уже покрыты, и подготовь недостающие сценарии в пределах поручения.
Рефакторинг с сохранением поведения проверяй существующими сценариями;
новый сценарий на каждую внутреннюю правку не требуется. Unit-тесты дополняют
спецификации проверками технических деталей.

Архитектурные решения, планы, объяснения и изменения документации не требуют
BDD-сценариев. Явный запрос «только черновик» или «сначала согласуем» означает
подготовку описания с открытыми вопросами, без автоматической реализации.
Другой формат по прямому поручению пользователя обозначь явно.

## От требования к сценарию

1. Найди основание требования: поручение, согласованный документ или контракт.
   Не превращай текущее поведение программы в требование автоматически.
   Уточни существенную неоднозначность; незаданные роли, лимиты и ошибки
   не выдавай за согласованные решения.
2. Определи исходное состояние, действие, наблюдаемый результат и существенные
   побочные эффекты. Один сценарий проверяет одно связное обязательство.
   Выбери значимые отрицательные и граничные случаи; запрет дополни
   разрешённым случаем, чтобы реализация «запретить всё» не прошла проверку.
3. Используй существующий идентификатор требования. Если его нет, дай короткий
   стабильный идентификатор, например `TASK-001`, и включи его в название
   сценария. Укажи основание рядом со сценарием или в ссылающемся документе;
   отдельный реестр соответствий не требуется.
4. Пиши `Given / When / Then` или `Дано / Когда / Тогда`. Для русских ключевых
   слов добавляй `# language: ru` и проверяй поддержку локализации движком.
   Варианты одного правила оформляй через `Scenario Outline / Examples`
   (`Структура сценария / Примеры`), разные правила — отдельными сценариями.

Для обсуждения можно использовать [черновик сценария](../templates/product-scenario.md.tmpl).
После автоматизации подробное поведение поддерживай в `.feature`; в документе
оставь основание, пояснения и ссылку на сценарий. Две независимо редактируемые
копии одних и тех же шагов не нужны.

## Проверяющий код

Сначала изучи существующие сценарии, фикстуры и конфигурацию движка.
Переиспользуй их; не создавай параллельную инфраструктуру без необходимости.

- Подключи сценарии к тестовому запуску и определи все их шаги. В pytest-bdd
  используй `scenarios(...)` или `@scenario` без дублирующих привязок, а шаги
  размещай в тестовом модуле или доступном `conftest.py`. Параметры извлекай
  через `parsers.parse`, результаты шагов передавай через `target_fixture`.
  Для другого движка используй его штатный механизм подключения.
- Вызывай настоящий компонент через подходящую публичную границу: API модуля,
  HTTP, CLI или UI. Выбирай уровень, который действительно проверяет требование;
  не каждое правило требует полного запуска приложения или браузера.
- Проверяй значимые данные и эффекты, включая отсутствие запрещённого эффекта.
  Ожидания выводи из требования, а не вычисляй алгоритмом проверяемой реализации.
  При ожидаемой ошибке проверяй конкретный тип или согласованный контракт ответа.
- Не реализуй продуктовую логику в шагах и не подменяй проверяемый компонент
  заглушкой. Подменять внешние зависимости на границе допустимо. Пустые шаги,
  `assert True` и подавление любых исключений не подтверждают поведение.
- Изолируй данные между сценариями, освобождай ресурсы фикстурами. Используй
  тестовое окружение; не отправляй реальные письма и не меняй рабочие данные.
  Ожидание асинхронного результата ограничивай временем и проверяемым условием.

Для AI-функций проверяй ограничения действий по реальным вызовам и состоянию:
например, запрет отправки без подтверждения — по отсутствию отправки.
Качество ответа модели оценивай по отдельно определённым критериям;
один удачный ответ не доказывает устойчивость поведения. Не вызывай платные
модели без разрешения и явно указывай недетерминированность проверки.

## Пример подключения на Python

Пример ниже иллюстрирует условное требование `TASK-001`: повтор создания
с тем же ключом и текстом возвращает существующую задачу без дубликата.
Это не требование к пустому шаблону и не готовый тест в этом репозитории.

Предполагается согласованный публичный интерфейс `app.tasks.TaskService`:
`create(key=..., text=...)` возвращает объект с `id` и `text`, `list()` —
список задач; новый экземпляр имеет изолированное пустое состояние.
Адаптируй импорт, вызовы и изоляцию к настоящему приложению. При отсутствии
такого интерфейса укажи блокировку, не создавай фиктивный сервис ради успеха.

В примере сценарий расположен в
`tests/acceptance/features/task_creation.feature`:

```gherkin
# language: ru
Функциональность: Создание задач без дубликатов

  Сценарий: TASK-001. Повтор возвращает существующую задачу
    Дано пустой сервис задач
    Когда дважды создают задачу "Подготовить отчёт" с ключом "req-42"
    Тогда оба ответа указывают на одну задачу
    И сохранена одна задача с текстом "Подготовить отчёт"
```

Связанный тестовый модуль `tests/acceptance/test_task_creation.py`:

```python
from pytest_bdd import given, parsers, scenarios, then, when

from app.tasks import TaskService


scenarios("features/task_creation.feature")


@given("пустой сервис задач", target_fixture="service")
def empty_service():
    service = TaskService()
    assert service.list() == []
    return service


@when(
    parsers.parse('дважды создают задачу "{text}" с ключом "{key}"'),
    target_fixture="responses",
)
def repeat_creation(service, text, key):
    first = service.create(key=key, text=text)
    second = service.create(key=key, text=text)
    return first, second


@then("оба ответа указывают на одну задачу")
def same_task(responses):
    first, second = responses
    assert first.id is not None
    assert first.id == second.id


@then(parsers.parse('сохранена одна задача с текстом "{text}"'))
def one_saved_task(service, responses, text):
    tasks = service.list()
    assert len(tasks) == 1
    assert tasks[0].text == text
    assert tasks[0].id == responses[0].id
```

Проверяется последовательный повтор в одном окружении. Конкурентность,
разделение пользователей и сохранность после перезапуска требуют отдельных
сценариев, если входят в требование. Для БД используй фикстуры изоляции и
очистки проекта вместо предположения о состоянии нового экземпляра сервиса.

Локализация поддерживается в pytest-bdd начиная с 8.0; механизм привязок и
фикстур описан в [документации pytest-bdd](https://pytest-bdd.readthedocs.io/en/stable/).
Синтаксис сценариев — в [справочнике Gherkin](https://cucumber.io/docs/gherkin/reference/).
Проверь совместимость версий Python, pytest и pytest-bdd в выбранной среде.

## Запуск и подтверждение результата

<remove_after_instruction_complete>

Настрой окружение при первой продуктовой задаче по `development.md`.
Для приведённой структуры после установки зависимостей и подключения приложения
типовой запуск из корня проекта в его Python-окружении выглядит так:

```sh
python -m pytest tests/acceptance/ --collect-only -q
python -m pytest tests/acceptance/ -v
```

Эти команды — пример, не проверенная команда пустого шаблона. Реальный способ
входа в окружение и запуска запиши в `development.md`; для другого движка
укажи его команды. Окружение и пример выше в этом шаблоне не исполнялись.
После подтверждения реальной команды в `development.md` удали этот блок.

</remove_after_instruction_complete>

Сопоставь собранные проверки со всеми сценариями и строками примеров в объёме
задачи: исключи непривязанные файлы и дубли. Сбор тестов не заменяет выполнение
шагов. При новом поведении и доступной реализации проверь, что сценарий
обнаруживает нарушение, затем реализуй изменение, если оно поручено.
При уже реализованном поведении искусственное падение не требуется.

Запусти затронутые сценарии и согласованные регрессионные проверки.
Не ослабляй ожидания, не добавляй пропуски и не скрывай код возврата ради успеха.
При подключении к общей проверке проекта и CI сохраняй неуспешный результат
движка; незавершённые шаги и отсутствие ожидаемых сценариев не считай успехом.
Прохождение сценариев не доказывает полноту требований — её оценивай при ревью.

В отчёте укажи проверенные требования, команды, число прошедших, упавших и
пропущенных проверок, ограничения и наличие изменений продуктового кода.
Различай состояния:

| Статус | Основание |
| --- | --- |
| `DRAFT` | Описание или каркас подготовлены, исполнение ещё не подтверждено. |
| `BLOCKED` | Запуск невозможен: отсутствует интерфейс, окружение или доступ. |
| `RED` | Проверка выполнилась и обнаружила нарушение требования. |
| `GREEN` | Все ожидаемые проверки в заявленном объёме выполнены и прошли без пропусков. |

Ошибки импорта, неопределённые шаги и недоступное окружение не доказывают `RED`:
исправь причину либо укажи `BLOCKED`. В режиме «только спецификации» допустим
подтверждённый `RED` без исправления продукта. Частичный успех не объявляй общим
`GREEN`; локальный запуск не выдавай за пройденный CI.
